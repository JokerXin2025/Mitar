# Lean2TeX 模块说明

Lean2TeX 是 Mitar 中负责“Lean 表达式语义渲染”的 Python 模块。它接收 ProofScript
导出的 ExprJSON，将 Lean elaboration 后的表达式转换为面向展示的语义树，再结合宏配置、
运算优先级、变量命名和排版模式生成 TeX。

本文面向以下读者：

- 需要维护 Lean2TeX 转换与渲染代码的开发者；
- 需要为 Mathlib 常量增加显示规则的宏配置作者；
- 需要理解 Mitar 变量高亮、诊断报告和 proof 页面渲染链路的开发者；
- 需要扩展 ProofScript ExprJSON 通用语义字段的上游维护者。

## 1. 模块职责

Lean2TeX 的输入不是 Lean 源码，也不是 Lean pretty printer 输出，而是 ProofScript 导出的
ExprJSON。它的主要职责包括：

1. 理解 ExprJSON 的表达式构造；
2. 展平 Lean 二叉 application 链；
3. 使用 ProofScript 导出的参数显式性信息过滤隐式参数和 typeclass instance；
4. 将 ExprJSON 转换为独立的 `DisplayNode` tree；
5. 根据变量类型分配稳定、易读的数学变量名；
6. 解析 binder 与 de Bruijn bvar 的绑定关系；
7. 根据宏配置生成数学符号和结构；
8. 根据优先级、结合性和 fixity 自动添加括号；
9. 在 formula 和 text mode 之间切换；
10. 为未知表达式生成可读 fallback，而不是静默丢失内容；
11. 收集缺失宏、参数错误和未知节点等诊断；
12. 为 fvar、binder、bvar 生成 KaTeX `htmlData`，支持页面联动高亮。

Lean2TeX 不负责：

- 解析 Lean 源码；
- 调用 Lean elaborator；
- 推断 expression 是否为命题；
- 猜测 application 参数是否显式；
- 构建 Mitar 页面结构；
- 生成完整自然语言证明；
- 在前端重新推断 Lean 变量身份。

这些 Lean 语义信息应由 ProofScript 在 ExprJSON 中提供。

## 2. 总体数据流

当前完整数据流如下：

```text
Lean Expr
  -> ProofScript ExprJSON
  -> SemanticConverter
  -> DisplayNode tree
  -> MacroRegistry
  -> LayoutRenderer
  -> TeX
  -> KaTeX HTML
  -> Mitar 页面交互
```

各阶段的边界是有意设计的：

- `SemanticConverter` 理解 Lean/ExprJSON 语义，但不负责最终 TeX 排版；
- `MacroRegistry` 管理声明到显示宏的映射；
- `LayoutRenderer` 理解 TeX、优先级和 mode，但不直接解析 ExprJSON；
- JavaScript 只根据已经生成的 identity 做高亮，不猜测 Lean 语义。

## 4. ExprJSON 输入契约

Lean2TeX 当前面向新版 ProofScript ExprJSON，不包含旧 schema 参数索引兼容层。

### 4.1 通用字段

每个 Expr 节点应包含：

```json
{
  "kind": "...",
  "isProp": false
}
```

可选字段：

```json
{
  "sourceRange": {
    "file": "/project/Example.lean",
    "start": 120,
    "stop": 131
  }
}
```

其中 `start`、`stop` 是 UTF-8 byte offset。

### 4.2 Application

ProofScript 保留 Lean Expr 的二叉 application：

```json
{
  "kind": "app",
  "fn": {},
  "arg": {}
}
```

同时提供展平后的语义字段：

```json
{
  "kind": "app",
  "headConstant": "HAdd.hAdd",
  "arguments": [
    {
      "expr": {},
      "binderInfo": "implicit",
      "isExplicit": false,
      "isTypeclass": false
    },
    {
      "expr": {},
      "binderInfo": "instImplicit",
      "isExplicit": false,
      "isTypeclass": true
    },
    {
      "expr": {},
      "binderInfo": "default",
      "isExplicit": true,
      "isTypeclass": false
    }
  ]
}
```

`headConstant` 使用 fully-qualified Lean declaration name。非 constant head 为 `null`。

参数字段可能为 `null`：

```json
{
  "binderInfo": null,
  "isExplicit": null,
  "isTypeclass": null
}
```

这表示 ProofScript 无法可靠找到对应 telescope binder。Lean2TeX 会把此类参数作为未知的
过应用参数保留下来，不会直接丢弃。

### 4.3 常见节点

Lean2TeX 支持以下 ExprJSON kind：

| kind | 主要字段 | DisplayNode kind |
|---|---|---|
| `const` | `name`, `levels` | `const` |
| `lit` | `lit.kind`, `lit.value` | `literal` |
| `fvar` | `id`, `name`, `type` | `fvar` |
| `bvar` | `index` | `bvar` |
| `app` | `fn`, `arg`, `headConstant`, `arguments` | 宏 kind 或 `application` |
| `forall` | `name`, `type`, `body`, `binderInfo` | `forall` |
| `lam` | `name`, `type`, `body`, `binderInfo` | `lambda` |
| `let` | `name`, `type`, `value`, `body` | `let` |
| `proj` | `fieldName`, `structName`, `index`, `expr` | `projection` |
| `sort` | `level` | `sort` |
| `mvar` | `id`, optional `name` | `metavariable` |
| `mdata` | `expr` | 透明转发到内部节点 |

## 5. DisplayTree 数据模型

`model.py` 中的核心类型是：

```python
@dataclass
class DisplayNode:
    macro_name: str
    kind: str = ""
    children: list["DisplayNode"] = field(default_factory=list)
    style_name: str | None = None
    metadata: dict[str, Any] = field(default_factory=dict)
```

示例：`n + 1` 在 Lean 中可能有 6 个 elaborated 参数，但 DisplayTree 只保留两个显式数学
参数：

```python
DisplayNode(
    macro_name="HAdd.hAdd",
    kind="operator",
    children=[
        DisplayNode(macro_name="n", kind="fvar"),
        DisplayNode(macro_name="1", kind="literal"),
    ],
    metadata={
        "headConst": "HAdd.hAdd",
        "rawArgumentCount": 6,
        "selectedArgumentIndices": [4, 5],
    },
)
```

常见 metadata：

- `leanName`：原 Lean 名称；
- `headConst`：application 头部常量；
- `rawArgumentCount`：原始展平参数数目；
- `selectedArgumentIndices`：被选中的显式参数索引；
- `fvarId`：Lean fvar identity；
- `bindId`：binder identity；
- `bindRef`：bvar 对应 binder identity；
- `typeName`：变量命名使用的类型名；
- `classification`：`proposition`、`proof`、`data`、`type`、`unknown`；
- `isProp`：ProofScript 导出的命题判断；
- `sourceRange`：可选源码范围；
- `originalExprKind`：来源 ExprJSON kind。

## 6. SemanticConverter

`SemanticConverter` 是 ExprJSON 的唯一主要语义入口。

### 6.1 Application 转换

转换过程：

1. 使用二叉 `fn`/`arg` 展平 application；
2. 读取 `headConstant`；
3. 应用 alias；
4. 应用 normalization；
5. 查找对应 Macro；
6. 若宏使用 `arguments = "explicit"`，根据 `arguments[].isExplicit` 选择 children；
7. `isExplicit = null` 的参数作为 trailing application 保留；
8. 未配置 application 转换为通用 `application` 节点并产生诊断。

缺少新版 `arguments` 描述时不会猜测 typeclass 参数。此类输入应被视为无效或不完整的新
schema 数据，并通过诊断/fallback 暴露。

### 6.2 Normalization

支持四种 operation：

| operation | 行为 |
|---|---|
| `select` | 选择原 application 的某个参数作为整个结果 |
| `rename` | 将常量名改为另一个显示宏名称 |
| `drop` | 丢弃 application 参数 |
| `reorder` | 按配置索引重排参数 |

例如：

```toml
[[normalization]]
name = "OfNat.ofNat"
operation = "select"
argument = 1
```

### 6.3 FVar 分类

分类规则基于 ProofScript 的 `isProp`：

```text
P : Prop -> P.isProp = true                       -> proposition
h : P    -> h.isProp = false, h.type.isProp=true -> proof
x : Nat  -> x.isProp = false                     -> data
α : Type -> type
```

该分类影响变量命名池：

- proposition 使用 `Prop` 池，例如 `P,Q,R`；
- proof 使用 `Proof` 池，例如 `h,h_1,h_2`；
- data 根据具体类型池，例如 `Nat -> n,m,i`；
- type 使用 `Type` 池，例如 `\alpha,\beta`。

### 6.4 Binder 与 BVar

Lean 的 bvar 使用 de Bruijn index：

```text
index 0 = 最内层 binder
index 1 = 外一层 binder
```

SemanticConverter 维护 binder stack，将索引解析为明确引用：

```python
binder.metadata["bindId"] = "e3:b0"
bvar.metadata["bindRef"] = "e3:b0"
```

每次 `convert()` 使用独立 tree scope，例如 `e3`，防止不同 proof step 中都出现 `b0` 时错误
联动。

当前 identity 范围：

- fvar：通过 `fvarId` 在 theorem 内稳定；
- binder/bvar：只在单个 DisplayTree 内稳定；
- 不跨 proof step 猜测 `intro` 前后的 binder/fvar provenance。

## 7. 宏系统

宏配置位于：

```text
Lean2TeX/config/macros.toml
```

### 7.1 固定参数宏

```toml
[[macro]]
name = "HAdd.hAdd"
kind = "operator"
arguments = "explicit"
styles = [
  {
    name = "formula",
    mode = "formula",
    template = "#0+#1",
    fixity = "infix",
    precedence = 65,
    associativity = "left",
    child_roles = ["left", "right"]
  }
]
```

`#0`、`#1` 引用 SemanticConverter 已投影后的 children，而不是 Lean 原始参数。

### 7.2 常量宏

```toml
[[macro]]
name = "Nat"
kind = "const"
arguments = []
styles = [
  { name = "formula", mode = "formula", template = "\\mathbb{N}", fixity = "atom", precedence = 100 }
]
```

### 7.3 动态参数宏

动态宏使用：

```toml
dynamic_arity = true
```

模板使用 `#*`：

```toml
styles = [
  { name = "formula", mode = "formula", template = "\\left(#*\\right)", separator = ", " }
]
```

固定参数宏不能使用 `#*`；动态宏必须使用 `#*`。

### 7.4 Alias

```toml
[[alias]]
name = "Set.Mem"
target = "Membership.mem"
```

Alias 可以多级解析，但不能形成 cycle。加载时发现 cycle 会抛出 `L2T007`。

### 7.5 Relation

Calc 的 relation 通常是半应用表达式，只需要关系符号：

```toml
[[relation]]
name = "LE.le"
symbol = "\\leqslant"
```

`Expr2TeX.render_relation()` 使用该表返回符号。

## 8. 宏配置验证

`load_macros_toml()` 在加载阶段检查：

- `arguments` 必须是 `"explicit"` 或非负整数数组；
- Macro 至少有一个 style；
- 同一 Macro 内 style 名唯一；
- `mode` 只能是 `formula` 或 `text`；
- `fixity` 必须是允许值；
- `associativity` 必须是 `left`、`right` 或 `none`；
- precedence 必须是 `0..100` 整数；
- 固定模板的 `#0..#N` 必须连续；
- 固定模板不能引用不存在的 child；
- 动态宏和 `#*` 必须一致；
- alias 不能形成 cycle；
- normalization operation 必须合法。

配置错误会在加载时失败，而不是等页面构建后静默产生错误 TeX。

## 9. 布局与自动括号

`LayoutRenderer` 使用统一 layout 属性：

- `fixity`
- `precedence`
- `associativity`
- child position
- mode

优先级越大，绑定越紧。当前常用层级：

| 表达式 | precedence |
|---|---:|
| 原子、变量、常量 | 100 |
| 函数应用 | 90 |
| 幂 | 80 |
| 一元负号 | 75 |
| 乘除 | 70 |
| 加减 | 65 |
| 关系 | 50 |
| 否定 | 45 |
| 合取 | 40 |
| 析取 | 35 |
| 蕴含 | 30 |
| 等价 | 25 |
| 量词 | 20 |

基础规则：

```python
if child.precedence < parent.precedence:
    parenthesize(child)
```

优先级相等时根据结合性和 child 位置判断。例如：

- 左结合运算的右 child 同级时保守加括号；
- 右结合运算的左 child 同级时加括号；
- `associativity = "none"` 的同级嵌套关系保守加括号。

因此可正确区分：

```text
(a + b) * c
a * (b + c)
(a ^ b) ^ c
a ^ (b ^ c)
```

## 10. Formula/Text Mode

每个 `MacroStyle` 指定：

```toml
mode = "formula"
```

或：

```toml
mode = "text"
```

转换规则：

- formula child 进入 text parent：包为 `$...$`；
- text child 进入 formula parent：包为 `\text{...}`；
- text 中已有数学分隔片段时进行分段转换，避免在 `\text{}` 内生成嵌套 `$...$`。

例如中文逻辑宏：

```toml
template = "#0且#1"
mode = "text"
```

其中两个 proposition child 会自动作为行内数学插入中文文本。

## 11. 变量命名系统

配置文件：

```text
Lean2TeX/config/variable.toml
```

示例：

```toml
[[type]]
name = "Nat"
default = "n"
var_names = ["n", "m", "i", "j", "k", "p", "q"]
```

分配策略：

1. 从类型专属名字池中选择第一个未使用名称；
2. 池耗尽后使用 `{default}_{n}`；
3. 未知类型使用 `{typeName}{n}`；
4. 所有类型共享已分配名称集合，避免跨类型重名；
5. 同一个 `fvarId` 通过 cache 始终复用相同名字；
6. 用户明确 binder 名优先保留；
7. shadowing 时生成 `x_1`、`x_2`；
8. binder 离开作用域后释放名字；
9. theorem 结束时调用 `renderer.reset()` 清空状态。

当前内置类型池：

- `Real`
- `Nat`
- `Int`
- `Rat`
- `Prop`
- `Proof`
- `Type`

## 12. Fallback 行为

缺少宏配置时不返回空字符串。

### 未知常量

```text
MyNamespace.foo
-> \operatorname{foo}
```

### 未知 Application

```text
foo a b
-> \operatorname{foo}\left(a,b\right)
```

### Lambda

```text
fun x => f x
-> x \mapsto f(x)
```

### Let

```text
let x := a; body
-> \operatorname{let}\ x := a\ \operatorname{in}\ body
```

### Projection

优先显示 `fieldName`；缺失时显示 projection index。

### Metavariable

```tex
\square
```

### 未知节点

```tex
\texttt{[unknown: kind]}
```

同时产生诊断。

## 13. 诊断系统

诊断模型：

```python
@dataclass(frozen=True)
class RenderDiagnostic:
    severity: str
    code: str
    message: str
    constant: str | None
    path: tuple[int, ...]
    source_range: dict | None
```

当前错误码：

| code | 含义 |
|---|---|
| `L2T001` | 缺少宏配置 |
| `L2T002` | 参数索引或参数数量错误 |
| `L2T003` | 无法解析 bvar |
| `L2T004` | 模板引用不存在的 child 或动态模板不匹配 |
| `L2T005` | 宏/alias/style 定义冲突 |
| `L2T006` | 未找到可用 style |
| `L2T007` | alias cycle |
| `L2T008` | 非法配置或 layout 值 |
| `L2T009` | 使用 application fallback |
| `L2T010` | 未知或畸形 ExprJSON 节点 |

获取当前诊断：

```python
renderer.diagnostics
renderer.diagnostics_dict()
```

Mitar 页面构建会生成：

```text
.Mitar/build/lean2tex-report.json
```

报告包含：

- 总诊断数量；
- 按错误码统计；
- 缺失宏命中统计；
- theorem 名；
- proof JSON 路径；
- ExprJSON child path；
- 可选 sourceRange。

未知宏通常是 warning，不会阻止普通页面构建；非法配置在加载时直接失败。

## 14. 交互式变量高亮

变量在 TeX 中通过 KaTeX `\htmlData` 携带 identity：

```tex
\htmlData{l2t-kind=fvar,l2t-ref=f-0123456789abcdef}{x}
```

### FVar

Identity 基于 ProofScript 的 `fvarId` 生成，并经过 SHA-256 截断，避免把 Lean 内部名称直接
写入 HTML attribute。

同一 theorem 内相同 `fvarId` 的所有出现共享 `data-l2t-ref`。

### Binder/BVar

Binder 与对应 bvar 共享作用域化 identity：

```text
e3:b0
```

该 identity 同样经过 hash 后写入 HTML。每次 `convert()` 都创建独立 expression scope，
因此不同 proof step 中的 `b0` 不会错误联动。

### 前端行为

`js/lean2tex.js` 使用事件委托：

1. 捕获 `pointerover`/`pointerout`；
2. 查找最近的 `[data-l2t-ref]`；
3. 将查询范围限制在最近的 `.theorem-proof`；
4. 给同 identity 节点添加或移除 `data-l2t-active`。

CSS 中：

- fvar/bvar 使用蓝色高亮；
- binder 使用略偏紫色的高亮；
- 支持 `prefers-reduced-motion`。

KaTeX trust 只允许 `\htmlData`，没有使用不受限制的 `trust: true`。

## 15. 公共 API

### 加载默认配置

```python
from Lean2TeX import load

renderer = load()
```

也可指定配置：

```python
renderer = load(
    variable_path="custom-variable.toml",
    macros_path="custom-macros.toml",
)
```

### 直接渲染 ExprJSON

```python
tex = renderer.render(expr)
```

### 分阶段转换

```python
display = renderer.convert(expr)
tex = renderer.render_display(display, style="formula")
```

分阶段 API 适合：

- 测试 DisplayTree；
- 调试参数投影；
- 添加交互 metadata；
- 在渲染前修改或检查 tree；
- 后续实现其他输出后端。

### 渲染 Calc Relation

```python
symbol = renderer.render_relation(relation_expr)
```

### 重置 theorem 状态

```python
renderer.reset()
```

Mitar 当前为每个 theorem 创建一个 `ProofEngine`，因此 theorem 之间天然隔离；如果外部调用方
复用 renderer，则必须主动在 theorem 边界调用 `reset()`。

## 16. 如何新增宏

以新增一个二元运算为例。

### 第一步：确认 Lean declaration 名

从诊断报告或 ExprJSON 中找到：

```json
"headConstant": "MyNamespace.op"
```

### 第二步：检查参数描述

确认数学参数的 `isExplicit` 为 `true`，隐式类型和 instance 为 `false`。

### 第三步：添加配置

```toml
[[macro]]
name = "MyNamespace.op"
kind = "operator"
arguments = "explicit"
styles = [
  {
    name = "formula",
    mode = "formula",
    template = "#0 \\star #1",
    fixity = "infix",
    precedence = 68,
    associativity = "left"
  }
]
```

### 第四步：补测试

测试至少应覆盖：

- DisplayTree children 数目和顺序；
- 最终 TeX；
- 与高/低优先级运算嵌套时的括号；
- 隐式参数和 typeclass instance 未进入输出；
- 部分应用或过应用的 fallback。

### 第五步：运行真实构建

```bash
python3 -m unittest Lean2TeX.tests.test_render Lean2TeX.tests.test_semantic -v
mitar make /path/to/project
```

然后检查：

```text
.Mitar/build/lean2tex-report.json
```

## 18. 当前边界与后续方向

### 18.1 Mathlib 宏覆盖

当前配置覆盖常用逻辑、算术、关系、集合和部分投影，但不会预先覆盖全部 Mathlib declaration。
未知常量会安全 fallback，并在报告中统计。

### 18.2 Source Range 覆盖率

Mitar 已支持 `sourceRange`，但实际字段是否存在取决于 Lean expression metadata 中是否保留
Syntax range。当前真实 fixture 中该字段覆盖率较低。

### 18.3 跨 Proof Step Binder Provenance

当前不尝试把：

```text
forall binder/bvar
  -> intro
  -> fvar
```

跨 proof step 关联为同一 identity。要严格支持该能力，需要 ProofScript 导出通用 provenance，
不能在 Python 或 JavaScript 中根据名称和结构猜测。

### 18.4 多 Style

框架已支持 `formula`、`prose-zh`、`debug` 等 style，但当前宏配置主要以 `formula` 为主。
未来可以继续扩充：

- `prose-en`
- `compact`
- 页面或 CLI 级 style 选择

## 19. 设计原则

维护和扩展 Lean2TeX 时应遵循：

1. Lean 语义判断应尽量来自 ProofScript，而不是 Python 字符串猜测；
2. ExprJSON 解析只放在 SemanticConverter/Expr helper 层；
3. LayoutRenderer 不应理解 de Bruijn index 或 application telescope；
4. JavaScript 不应根据变量文本推断 identity；
5. 缺少宏时必须可见 fallback，并产生诊断；
6. 配置错误应尽早失败；
7. 新宏优先使用 `arguments = "explicit"`；
8. 修改括号、mode 或模板输出时补 golden test；
9. schema 变化后先清理旧 ProofScript 输出再验证；
10. 不为单一下游需求向 ProofScript 增加专用字段。
